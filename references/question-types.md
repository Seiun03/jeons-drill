# 문제 유형과 채점 기준

`pick` 출력의 `level`, `variant`, `type`을 보고 아래 정의대로 문제를 만든다.

---

## 1. 객관식 (level: mc)

### 공통 규칙
- 선지는 **4개**, 번호 `1)`~`4)`. 정답은 반드시 `mc_answer_position`번.
- 오답 선지 재료 순서: `misconceptions` → `related` 개념(헷갈리기 쉬운 이웃 개념) → 자료 속 비슷한 용어.
- 선지 길이와 문장 구조를 비슷하게 맞춘다. 정답만 유독 길거나 구체적이면 안 된다.
- 금지: "모두 옳다/모두 틀리다", 말장난, 부정어 두 번, 자료 밖 지식이 필요한 선지.
- 사용자는 `번호 + 확신도`로 답한다. 예: `2 확실`, `3 애매`, `1 찍음`. 확신도를 안 쓰면 `확실`로 본다.

### 결과 기록
| 사용자 답 | result |
|---|---|
| 정답 + 확실 | correct |
| 정답 + 애매 | unsure (일반 모드에선 정답과 같게 처리되고, 좆됐어 모드에선 승급하지 않음) |
| 정답 + 찍음 | guess |
| 오답 (확신도 무관) | wrong |

record에는 항상 `--asked <pick이 준 level>`을 붙인다.

`확실`로 틀렸으면 해설에서 "확신했는데 틀린 건 오개념이 굳어 있다는 뜻"이라고 짚고 더 꼼꼼히 설명한다.

### 변형
| variant | 만드는 법 |
|---|---|
| def_to_term | 정의/설명을 주고 → 해당 **용어** 고르기 |
| term_to_def | 용어를 주고 → 맞는 **정의** 고르기 |
| example_to_concept | 구체적 상황·사례를 주고 → 어떤 개념의 예인지 고르기 |
| not_true | 개념에 대한 설명 4개 중 **옳지 않은 것** 고르기 (정답 = 틀린 문장. 문제에 "옳지 않은 것"을 굵게) |
| correct_statement | 원리·과정에 대한 설명 중 옳은 것 고르기 |
| cause_effect | "A가 일어나면 어떻게 되는가" 결과 고르기 |
| order | 과정의 단계 순서로 옳은 것 고르기 |
| compute_choose | 강의 예제의 숫자를 바꾼 계산 문제, 결과 고르기. 오답은 흔한 실수(부호, 공식 혼동, 단위)로 만든 값 |
| formula_choose | 상황에 맞는 공식·식 고르기 |
| interpret | 계산 결과나 식의 의미 해석 고르기 |
| output_choose | 짧은 코드의 출력 고르기 |
| bug_line | 줄 번호가 붙은 코드에서 버그가 있는 줄 고르기 |
| complexity_choose | 시간/공간 복잡도 고르기 |
| fill_blank_choose | 코드의 빈칸에 들어갈 코드 고르기 |

## 2. 단답식 (level: short)

### 공통 규칙
- 답이 한 단어~한 줄로 **하나로 정해지는** 문제만 낸다.
- 정답 판정:
  - 동의어, 한/영 표기(`스택` = `stack`), 대소문자, 띄어쓰기 차이 → correct
  - 용어 철자가 틀림(예: `Dijkstra`를 `Dikstra`) → **partial**, 정확한 표기를 알려 준다
  - 의미가 다르거나 더 넓은/좁은 개념 → wrong
- 수식 답은 평문 입력 허용: `x^2`, `sqrt(2)`, `1/3`, `pi`, `e^x`. 동치 판정은 **sympy로**.

### 변형
| variant | 만드는 법 |
|---|---|
| write_term | 정의를 주고 용어 쓰기 |
| fill_blank | 자료의 핵심 문장에서 핵심어 하나를 빈칸으로 |
| write_definition | 용어를 주고 한 문장 정의 쓰기 (key_points의 첫 포인트 기준으로 채점) |
| key_term | 과정·원리 설명을 주고 핵심 용어 쓰기 |
| compute | 숫자를 바꾼 계산 문제, 값 쓰기. 정답은 출제 전에 코드로 계산 |
| write_formula | 공식 쓰기 |
| write_output | 코드의 출력 그대로 쓰기 (공백·줄바꿈까지 비교, 사소한 공백 차이는 correct로 하되 지적) |
| fill_blank_line | 코드의 빈칸 한 줄 직접 쓰기. 손코딩 기준으로 문법까지 채점 |
| write_complexity | 복잡도를 Big-O로 쓰기 |

## 3. 서술형 (level: essay)

### 채점 기준표
`key_points`를 채점표로 쓴다. 채점 결과를 이렇게 보여 준다:

```
✅ 포함: 균형 인수 정의, 허용 범위 -1~1
❌ 누락: 위반 시 회전으로 복구한다는 점
⚠️ 틀린 서술: "루트에서만 검사한다" → 모든 노드에서 검사
점수: 60/100 → 부분 정답
```

- 점수 = 포함한 key_points 비율 기반, 틀린 서술은 감점.
- **70점 이상 → correct, 40~69 → partial, 40 미만 → wrong.** `--score`로 점수도 기록.
- 채점 후 **모범답안**을 보여 준다 (자료 표현 기반, 시험 답안 길이로).
- 키워드만 나열하고 관계를 설명하지 않았으면 해당 포인트는 반만 인정한다.

### 변형
| variant | 만드는 법 |
|---|---|
| compare | `related` 개념과 비교해서 공통점·차이점 서술 |
| explain_with_example | 개념을 정의하고 예를 들어 설명 |
| explain_why | 왜 그렇게 되는지/왜 필요한지 서술 |
| predict_and_explain | 조건을 바꾼 상황을 주고 결과를 예측하고 이유 서술 |
| full_solution | 풀이 과정 전체를 쓰는 계산 문제 (아래 수학 규칙) |
| derive_or_prove | 공식 유도나 간단한 증명 |
| write_function | 함수 작성 (아래 코드 규칙) |
| explain_code | 주어진 코드가 무엇을 하는지, 핵심 줄의 역할 서술 |

## 4. 수학 규칙 (type: formula)

- 변형 문제는 강의 예제 구조를 유지하고 숫자만 바꾼다. 답이 깔끔하게 떨어지는 숫자를 고른다(출제 전 코드로 확인).
- 출제 전에 Python으로 정답을 계산해 둔다. 계산이 자료의 방법과 일치하는지도 확인한다.
- 풀이 과정 채점(full_solution): 단계별로 확인한다.
  - 방법 선택이 맞는지 → 식 세우기 → 계산 → 최종 답
  - 중간에 계산 실수가 있으면 그 단계 이후는 "실수를 반영한 값" 기준으로 방법이 맞는지 본다(부분 점수).
- 긴 풀이는 사용자가 사진을 첨부하거나 `answers/q<번호>.md`에 쓸 수 있다고 안내한다.

## 5. 코드 규칙 (type: code)

언어는 개념의 `language`, 없으면 concepts.json 최상위 `language`. **시험은 손코딩 기준.**

### 출제
- 출력·버그·빈칸 문제의 코드는 출제 전에 `.drill/tmp/`에서 실행해 결과를 확정한다.
- 코드는 10~25줄 이내, 줄 번호를 붙인다.
- 함수 작성 문제(write_function)는 함수 시그니처, 입력/출력 예시 2개, 제약 조건을 준다.

### 답안 제출
- 짧은 답은 채팅에 바로 쓴다.
- 함수 작성은 `answers/q<번호 3자리>.<확장자>`에 작성하고 "제출"이라고 하게 안내한다. 파일 이름을 문제에 적어 준다.

### 채점 (손코딩 기준이지만 문법도 엄격하게)
1. **문법 검사 먼저**: 컴파일/파싱해서 문법 오류를 찾는다. 오류마다 **줄 번호와 올바른 형태**를 짚는다(세미콜론, 괄호, 들여쓰기, 타입 선언, 오타 난 함수명 등). 문법 오류 하나당 감점.
2. **로직 검사**: 숨겨진 테스트를 실행한다 — 일반 케이스 2~3개, 경계(빈 입력, 원소 1개, 최대/최소), 예외 케이스. 통과/실패를 표로 보여 준다.
3. **리뷰**: 복잡도, 자료에서 배운 방식과 다른 점, 더 나은 방법.
4. 점수: 로직 70 + 문법 30에서 감점. 결과 매핑은 서술형과 같다(70↑ correct).

```
[문법] 2곳 감점 (-10)
  5행: for (i = 0; i < n; i++  →  닫는 괄호 누락
  9행: retrun  →  return
[테스트] 4/5 통과
  ✅ 일반 [3,1,2] → [1,2,3]
  ❌ 빈 배열 [] → 기대 [], 실제: 인덱스 오류
[리뷰] O(n²). 자료의 방식(p.22)은 ...
점수: 62/100 → 부분 정답
```

- 손코딩 시험에 필요 없는 부분(include, main 함수 등)은 문제에서 "생략 가능"이라고 명시한 경우만 봐준다.

## 6. 숙련 복습 · 복합 (level: mastered / combo)

드물게 나온다. 일반 문제보다 한 단계 깊게.

| variant | 만드는 법 |
|---|---|
| review_short | 이전과 다른 형태의 단답식 하나 (recent_questions와 겹치지 않게) |
| angle | 같은 개념을 다른 각도로: 반례 찾기, 적용 조건의 한계, 응용 상황, 거꾸로 묻기 |
| combo | `concepts`에 온 2~3개 개념을 **하나의 서술형**으로 엮는다. 비교, 함께 쓰이는 상황, 하나가 다른 하나의 전제인 관계 등. 모든 개념의 key_points를 합쳐 채점 |

| final_check | 마지막 점검. 짧은 단답식으로 핵심만 확인. 1분 안에 답할 수 있는 크기 |

문제 앞에 `🔁 복습`, `🧩 복합`, `⏰ 점검` 표시를 붙인다.

## 7. 출력 형식

### 문제
```
[Q12 · 객관식 · 3강] 
다음 설명에 해당하는 용어는?
"모든 노드에서 왼쪽과 오른쪽 서브트리의 높이 차이가 1 이하인 이진 탐색 트리"

1) 완전 이진 트리
2) AVL 트리
3) 레드-블랙 트리
4) 힙

답: 번호 + 확신도 (확실/애매/찍음)
```
- 문제에 출처는 붙이지 않는다(힌트가 되므로). 출처는 해설에만.
- 단답식은 마지막 줄에 `답: 한 단어~한 줄`, 서술형은 `답: 3~6문장 (또는 answers/q012.py)`.

### 정답일 때
```
✅ 정답! AVL 트리는 모든 노드의 균형 인수가 -1~1. [출처: 03_트리 p.14]
⬆️ 'AVL 균형 인수' → 단답식 승급
```

### 틀렸을 때
```
❌ 정답은 2) AVL 트리
- 왜: ...
- 네가 고른 1) 완전 이진 트리는 ... (어떤 점을 헷갈렸는지)
- 기억할 점: ...
[출처: 03_트리 p.14]

질문 있으면 해, 없으면 '다음'
```

### 묶음 형식 (좆됐어 모드, `pick --batch`)
```
[I'm fucked. 나는 좆됐어. 모드 · Q41~Q45]

Q41 · 객관식 · 2강
다음 중 ... 옳지 않은 것은?
1) ...  2) ...  3) ...  4) ...

Q42 · 단답식 · 5강
... 을 무엇이라 하는가?

(Q43~Q45 같은 방식)

답: 한 줄에 순서대로. 객관식은 번호+확신도 첫 글자
예) 2확 / 스택 / 3애 / O(n log n) / 1찍
```
- 선지가 짧으면 한 줄에 나란히, 길면 줄을 나눈다.
- 문제마다 다른 개념이므로 서로의 힌트가 되지 않게 확인한다.

채점 결과:
```
Q41 ✅  Q42 ❌  Q43 ⚠️애매  Q44 ✅  Q45 ❌찍음
⬆️ 승급 2 · ⬇️ 강등 1

❌ Q42 정답: 큐
- ... (3~4줄) [출처: 05_자료구조 p.8]
...
질문 있으면 해, 없으면 '다음'
```
